wacrm

A self-hosted CRM for the WhatsApp Business Cloud API, built as a single Next.js 16 deployable over Supabase. No separate backend service, no ORM, no job queue — every mechanism described below was traced to a specific file and line in this working copy (package.json version 0.8.0).

Framework Next.js 16 App Router, React 19 Database Supabase Postgres, RLS on every table Migrations 36 hand-written SQL files, no ORM Tenancy accounts + 4-tier RBAC Automation engines Automations (flat) + Flows (graph) Background work after() + externally-pinged cron, no queue

Simple developer mental model

Before the detail: five sentences that explain almost everything else in this document.

1. It's one app, not a distributed system

Every "service" is a folder under src/lib/. Route handlers under src/app/api/ are thin adapters: parse request → call a src/lib/ function → return JSON. There is no separate API server, no microservice boundary, no message broker.

2. Postgres RLS is the real authorization boundary

Row-Level Security policies (keyed on account_id via the is_account_member() SQL helper) are checked on every table, every query, from the RLS-respecting client. App-layer role checks in src/lib/auth/roles.ts exist for UI gating and API guards, but the database enforces tenancy independently.

3. One inbound webhook feeds three "brains"

Every customer WhatsApp message lands at one route handler, which sequentially offers it to the Flows engine, then the Automations engine, then the AI auto-reply — each one aware of whether an earlier one already "consumed" the message.

4. Service-role code paths police themselves

The webhook, both automation engines, and the public API's key-auth path all use a service-role Postgres client that bypasses RLS. Each of those code paths is individually responsible for re-checking that a row actually belongs to the claimed account_id — the database won't stop a mistake there.

5. Nothing runs unless something pings it

There's no worker process and no job queue. "Wait" steps and stale-run cleanup are rows in a table with a run_at timestamp, drained only when an external cron pings GET /api/automations/cron / GET /api/flows/cron. Skip that ping and those features simply stall.

1 · Architecture

2 · Data model & multi-tenancy

Schema of record is supabase/migrations/*.sql — 36 sequential, idempotent, hand-written files, applied manually via the Supabase CLI (no migration runner is wired into the build). The tenancy model was retrofitted in 017_account_sharing.sql: every domain table gained an account_id column, and RLS policies now check account membership rather than raw row ownership.

The tenancy primitive: is_account_member()

A single SECURITY DEFINER SQL function is the predicate behind essentially every RLS policy in the schema, and its role-ranking logic is deliberately mirrored — not re-derived — in TypeScript:

supabase/migrations/017_account_sharing.sql

CREATE FUNCTION is_account_member(
  target_account_id UUID,
  min_role account_role_enum DEFAULT 'viewer'
) RETURNS BOOLEAN
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = public AS $$
  SELECT EXISTS (
    SELECT 1 FROM profiles p
    WHERE p.user_id = auth.uid()
      AND p.account_id = target_account_id
      AND CASE p.account_role
            WHEN 'owner' THEN 4 WHEN 'admin' THEN 3
            WHEN 'agent' THEN 2 WHEN 'viewer' THEN 1 END
        >=
          CASE min_role
            WHEN 'owner' THEN 4 WHEN 'admin' THEN 3
            WHEN 'agent' THEN 2 WHEN 'viewer' THEN 1 END
  );
$$;

src/lib/auth/roles.ts

const ACCOUNT_ROLES = ["viewer","agent","admin","owner"];

function roleRank(role) {
  return ACCOUNT_ROLES.indexOf(role) + 1; // 1..4
}
function hasMinRole(role, min) {
  return roleRank(role) >= roleRank(min);
}

canManageMembers = (r) => hasMinRole(r, "admin");
canEditSettings  = (r) => hasMinRole(r, "admin");
canSendMessages  = (r) => hasMinRole(r, "agent");
canDeleteAccount     = (r) => r === "owner";
canTransferOwnership = (r) => r === "owner";

Example policy built on it, contacts (017_account_sharing.sql): any member can SELECT, but INSERT/UPDATE/DELETE require is_account_member(account_id, 'agent') — matching canSendMessages's agent-floor exactly. Settings-class tables (whatsapp_config, api_keys, webhook_endpoints, ai_configs) instead gate writes at 'admin', matching canEditSettings.

Notable schema details

  • Contact/conversation dedup is enforced, not just conventional. contacts.phone_normalized is a generated column with a unique partial index per account (022_contact_phone_dedup.sql); conversations got a matching unique (account_id, contact_id) index in 036_conversation_contact_dedup.sql, each preceded by a merge_duplicate_contacts() / merge_duplicate_conversations() one-time cleanup function that re-points every dependent row before the constraint goes live.
  • Realtime is enabled on messages, conversations, flow_runs, notifications, and member_presence — the inbox UI subscribes rather than polls (src/hooks/use-realtime.ts).
  • Two real security-fix migrations exist in this history and are worth reading before adding any new SECURITY DEFINER function: 032_fix_ai_knowledge_membership.sql downgrades the knowledge-base search RPCs from DEFINER to INVOKER (closing a cross-account RAG read), and 034_fix_profiles_update_rls.sql adds a trigger blocking a client from writing its own account_id/account_role (closing a tenant-hop/privilege-escalation hole). Both are tagged GHSA-fg5p-2qc3-jmxr in the SQL comments.
  • One schema inconsistency: message_templates gained an account_id column in migration 017 but its uniqueness constraint (014_message_templates_meta_integration.sql) is still UNIQUE(user_id, name, language), not account-scoped — two different agents in the same account could create same-named templates, unlike every other account-scoped unique index in the schema.

3 · Authentication & permissions

There are two independent auth systems in this codebase, and they don't share a code path: cookie/JWT session auth for the dashboard, and API-key auth for the public REST API. A third, informal mechanism — HMAC signature verification — authenticates inbound Meta webhooks (covered in §6).

3.2 Public API key auth (/api/v1/*)

Where the service-role (RLS-bypassing) client actually lives

Four privileged code paths need a Postgres client that isn't scoped to a logged-in user's cookies: the WhatsApp webhook, the Automations engine, the Flows engine, and the AI engine (the public API's key-auth path reuses one of these). Verification against the source found this is implemented as three near-identical, independently-defined supabaseAdmin() factories — src/lib/flows/admin-client.ts, src/lib/automations/admin-client.ts, src/lib/ai/admin-client.ts — plus a fourth inline copy in src/app/api/whatsapp/webhook/route.ts, all independently instantiating a client from SUPABASE_SERVICE_ROLE_KEY. The public API's key-auth path (src/lib/api-keys/store.ts, src/lib/auth/api-context.ts) imports the flows copy rather than a dedicated one. Functionally equivalent, but it means "does this call the service-role client and does it re-check tenancy" has to be verified in four places, not one — see §9.

5 · End-to-end workflows

5.1 Inbound WhatsApp message — the central pipeline

This is the single most architecturally interesting file in the repo: src/app/api/whatsapp/webhook/route.ts (all of the logic below, including handleStatusUpdate, processMessage, findOrCreateContact and findOrCreateConversation, is defined inline in this one route file, not split into separate lib modules).

Media (image/video/audio/document/sticker) is never stored by direct URL — the webhook verifies the media ID resolves with Meta, then persists a proxy path (/api/whatsapp/media/{id}); the real Meta CDN URL and access token never leave the server (src/app/api/whatsapp/media/[mediaId]/route.ts).

5.5 Signup, invitation, and account onboarding

New signups get a fresh personal accounts row and owner role atomically, via the handle_new_user() trigger on auth.users. 6 · Background processing

There is no Celery/BullMQ/Sidekiq-equivalent anywhere in this codebase. Everything asynchronous is one of three shapes:

after() inside a request

The webhook returns 200 immediately, then does all real work inside Next's after() callback — awaited, not a detached promise, because a serverless function can freeze the instant the response is sent. maxDuration = 60 on the route gives it headroom for per-media Meta verification calls.

Externally-pinged cron

GET /api/automations/cron drains "wait"-step queue rows; GET /api/flows/cron sweeps stale Flow runs into timed_out. Both require a header x-cron-secret matching AUTOMATION_CRON_SECRET, compared with timingSafeEqual, and return 503 until that env var is set. Nothing in Docker Compose or the app itself calls these — an operator must wire an external pinger.

Fire-and-forget, explicitly non-critical

AI usage logging, legacy-token re-encryption on read, and last_used_at touches on API keys are all "best effort" — wrapped so their failure never affects the caller's response.

One correction worth flagging against a naive reading of "background processing": GET /api/flows/cron is not a wait-step resumer like its Automations counterpart — Flows have no wait node type at all. It is purely a timeout sweeper for stalled runs.

Outbound webhooks to third-party subscribers (src/lib/webhooks/deliver.ts) are explicitly at-most-once, single attempt, 5s timeout — the code comment states plainly that durable retry-with-backoff "would need a queue/worker (a follow-up)". After 15 consecutive failures an endpoint is auto-disabled via record_webhook_failure().

9 · Architecture risks

Ranked by what's most likely to bite an operator or a contributor extending this code. "Confirmed" items were reproduced by reading the actual implementation, not inferred.

Scale risk

Rate limiter is in-memory and per-process

src/lib/rate-limit.ts holds every bucket (send, broadcast, public API, AI draft/auto-reply, invitations, admin actions) in a single process-local Map. The code comments this explicitly: a horizontally-scaled deploy (2+ instances) silently loses the shared limit — every cap in RATE_LIMITS becomes N× looser with no error, no warning.

Confirmed at src/lib/rate-limit.ts:9-14. Mitigation already pointed at in the code: swap the same interface for a Redis/Upstash-backed store before scaling past one instance.

Coupling risk

Service-role tenancy checks are duplicated across four call sites

Four independent supabaseAdmin() factories (flows, automations, ai, and an inline copy in the webhook route) each bypass RLS. "Does this specific call re-verify the row belongs to the claimed account" has to be individually true in every one of them — there's no single choke point that would catch a new service-role code path forgetting the check.

Confirmed via repo-wide grep for SUPABASE_SERVICE_ROLE_KEY. Today's call sites do the check correctly (e.g. runAutomationsForTrigger re-verifies contactId belongs to accountId) — the risk is in the next one that's added without following the pattern.

Dead feature

Two automation trigger types exist end-to-end except the dispatch call

time_based ("schedule") and conversation_assigned are both valid in the type system, the validator, and the trigger-selection UI — but no code path anywhere calls runAutomationsForTrigger with either of them automatically. A user can build and activate an automation on these triggers and it will simply never fire.

Confirmed by grepping every caller of runAutomationsForTrigger. Only reachable today via the manual/testing POST /api/automations/engine endpoint with an arbitrary trigger_type in the body.

Correctness

A Flow node type is allowed by the schema but not implemented

flow_nodes.node_type's CHECK constraint (and a code comment referencing a "v2") both admit http_fetch, but it's absent from FlowNodeType/FlowNodeConfig and from the engine's node-execution switch. A flow node of that type (however it got created) falls through to the "unknown node type" branch and fails the run.

Confirmed in src/lib/flows/types.ts and engine.ts's advanceFromNodeKey. Low likelihood in practice (the UI likely never emits this type), but a public-API or direct-DB path could trigger it silently.

Accepted / documented

Outbound webhook SSRF guard has a documented DNS-rebinding gap

src/lib/webhooks/ssrf.ts resolves and validates a hostname's IPs at check-time, then fetch()s separately — a host that resolves to a public IP at check time and a private one at connect time isn't caught. The code comments call this out as a known, accepted residual risk rather than an oversight.

Not a regression to fix reflexively — but worth knowing before treating the SSRF guard as airtight.

Staged rollout

CSP is report-only, not enforced

next.config.ts ships Content-Security-Policy-Report-Only rather than an enforced Content-Security-Policy — deliberately staged pending a clean bill of health across routes. Don't assume it's blocking anything in production yet.

Fixed, historical

Two real tenant-isolation vulnerabilities were already found and patched

Migration 032 closed a cross-account read on the AI knowledge-base search RPCs (they were SECURITY DEFINER when they should have been INVOKER); migration 034 closed a client-writable profiles.account_id/account_role that could be used to hop accounts or self-promote to owner. Both are tagged GHSA-fg5p-2qc3-jmxr.

Not a current risk — listed because the pattern (a new SECURITY DEFINER function, or a new client-writable privileged column) is exactly how both happened, and is worth extra scrutiny on any future migration.

Minor

Public API scope design has one wart

GET /api/v1/broadcasts/[id] (status polling, read-only) requires the broadcasts:send scope — there's no separate read-only broadcasts scope, so a key intended only to check delivery status must also carry send capability.
